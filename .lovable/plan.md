# نظام إدارة الأدوار والصلاحيات الاحترافي

## النتيجة المتوقعة
- تنشئ أدوار جديدة بأي اسم وتعدلها وتحذفها.
- لكل دور **قائمة صلاحيات تفصيلية** (عرض، إنشاء، تعديل، حذف + عمليات خاصة لكل وحدة).
- الـ Sidebar والداشبورد تظهر للمستخدم **فقط** الحاجات اللي عنده صلاحية فيها.
- قاعدة البيانات (RLS) تطبق نفس الصلاحيات على مستوى الـ API — حتى لو حد لعب في الواجهة.

---

## ١) قاعدة البيانات (Migration واحدة كبيرة)

### جداول جديدة
- `roles` — الأدوار (الاسم، الوصف، `is_system` للأدوار الافتراضية اللي مينفعش تتمسح).
- `permissions` — كل الصلاحيات المتاحة في النظام (key مثل `offices.edit`, `expenses.approve`، التسمية بالعربي، الوحدة).
- `role_permissions` — ربط (دور ↔ صلاحية).
- `user_role_assignments` — ربط (مستخدم ↔ دور). يحل محل `user_roles` تدريجيًا.

### دالة فحص الصلاحية
```sql
has_permission(_user uuid, _key text) returns boolean
```
SECURITY DEFINER، تنادي على `user_role_assignments → role_permissions`. تتسجل لكل الجداول.

### الصلاحيات المبدئية (≈ 90 صلاحية)
لكل وحدة من الـ 20 وحدة الموجودة: `view / create / edit / delete` + عمليات خاصة:
- **expenses**: `approve`, `reject`, `pay`
- **maintenance**: `assign`, `close`, `reopen`
- **contracts**: `renew`, `cancel`
- **invoices**: `record_payment`, `mark_overdue`
- **guards**: `view_salary`, `edit_salary`
- **users**: `manage_roles`, `deactivate`
- **tickets**: `close`, `escalate`
- **building_log**: `view`
- ... إلخ

### الأدوار الافتراضية (seed)
- `super_admin` — كل الصلاحيات (محمي، مينفعش يتمسح).
- باقي الـ ٥ أدوار الحالية تتحول لأدوار قابلة للتعديل بنفس صلاحياتها الحالية (عشان مفيش حد يفقد وصوله فجأة).

### الترحيل الآمن
- كل صف في `user_roles` ينسخ المقابل ليه في `user_role_assignments`.
- دالة `has_role(uid, role_name)` تتعدل تشتغل من النظام الجديد عشان كل الكود القديم يفضل شغال.
- بعد التأكد، الجداول القديمة تفضل موجودة كـ backup ومتقفلش.

### RLS — إعادة كتابة شاملة
كل سياسة على الـ 50+ جدول تتحول من:
```sql
USING (has_role(auth.uid(), 'super_admin'))
```
إلى:
```sql
USING (has_permission(auth.uid(), 'offices.view'))
WITH CHECK (has_permission(auth.uid(), 'offices.edit'))
```
- نظام **الفول-اكسس للسوبر-أدمن**: `has_permission` ترجع `true` تلقائيًا لو المستخدم في دور `super_admin`.
- المنطق ده يضمن إن لو حصل خطأ في الـ mapping السوبر أدمن مش هيتقفل.

## ٢) الواجهة

### صفحة جديدة: `/roles` (إدارة الأدوار)
- جدول بكل الأدوار + عدد المستخدمين في كل دور + عدد الصلاحيات.
- زر "دور جديد" → اسم + وصف.
- زر "تعديل الصلاحيات" → Dialog فيه الصلاحيات مجمعة حسب الوحدة، مع:
  - Checkbox لكل صلاحية.
  - زر "تحديد الكل" / "إلغاء الكل" لكل وحدة.
  - زر "اختر قالب جاهز" (محاسب / صيانة / أمن / استقبال) لتسريع الإعداد.
- زر حذف (مش متاح للأدوار `is_system`).

### تحديث صفحة المستخدمين
- بدل `Select` للأدوار الثابتة → multi-select من قائمة الأدوار الديناميكية.
- المستخدم يقدر يكون عنده أكثر من دور (الصلاحيات تتجمع).

### `auth-context.tsx` — تعديل
- يحمل **مجموعة صلاحيات** المستخدم (`Set<string>`) بدل قائمة أدوار.
- يضيف `hasPermission(key)` و `hasAnyPermission(keys[])`.
- يحتفظ بـ `hasRole()` للتوافق العكسي (يفحص اسم الدور).

### Sidebar (`app-sidebar.tsx`)
كل عنصر في القائمة مربوط بصلاحية. لو المستخدم معندوش الصلاحية، العنصر **ميظهرش**.

### الداشبورد (`/dashboard`)
- تتعرف "Widgets" متعددة (بطاقات إحصائيات، رسوم، قوائم).
- كل widget مربوط بصلاحية. الداشبورد يبني نفسه ديناميكيًا حسب صلاحيات المستخدم — مفيش بطاقات فاضية ولا أرقام صفر.
- لو المستخدم معندوش أي صلاحية عرض → رسالة "تواصل مع مدير النظام لتفعيل صلاحياتك".

### الأزرار داخل الصفحات
- كل زر إنشاء/تعديل/حذف/اعتماد يتلف في `<PermissionGate perm="...">` بحيث يختفي لو معندوش الصلاحية.

## ٣) خطة التنفيذ المرحلية (عشان منكسرش حاجة)

سأنفذها على **٤ مراحل** كل واحدة قائمة بذاتها وقابلة للاختبار:

1. **Migration ١**: الجداول الجديدة + seed الصلاحيات والأدوار + دالة `has_permission` + ترحيل المستخدمين الحاليين. النظام القديم يفضل شغال.
2. **الواجهة**: صفحة `/roles` + تحديث `auth-context` + `PermissionGate` + تحديث `Sidebar` + تحديث صفحة المستخدمين. هنا تقدر تختبر إن كل حاجة شغالة قبل ما نلمس الـ RLS.
3. **الداشبورد الديناميكي**: إعادة هيكلة `dashboard.tsx` كـ widgets.
4. **Migration ٢**: تحويل الـ RLS لكل الجداول من `has_role` لـ `has_permission`. مع تحديث الـ triggers الحساسة. (دي أخطر خطوة، هنعملها آخر حاجة بعد ما كل اللي قبلها متأكدين منه).

## ⚠️ مخاطر مهمة لازم تعرفها قبل الموافقة
1. **خطر فقدان الوصول**: لو حصل غلط في mapping الصلاحيات، مستخدمين ممكن يتقفلوا. الحماية: السوبر أدمن دايمًا فول-اكسس بشكل صريح في الكود.
2. **حجم التغيير**: مرحلة ٤ بتعدل ~150 سياسة RLS. ممكن يطلع خطأ في جدول مش متوقع.
3. **الأكواد القديمة**: في حوالي 30 trigger و function في قاعدة البيانات بتستخدم `has_role`. هنخليها شغالة عن طريق إن `has_role` تنادي على النظام الجديد داخليًا.
4. **مينفعش Rollback سهل** بعد المرحلة ٤. لازم نتأكد من المراحل ١-٣ كويس قبل ما نبدأ ٤.
