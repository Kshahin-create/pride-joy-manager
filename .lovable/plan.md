
# تطوير دورة حياة أمر العمل (Work Order Lifecycle)

الهدف: تحويل أوامر العمل من 4 حالات بسيطة إلى دورة احترافية كاملة بـ 6 مراحل، مع توثيق كامل (مصدر، صور قبل/بعد، مواد، ساعات، اعتماد).

---

## 1. الحالات الجديدة (Workflow)

```text
مفتوح ──► معلّق للتعيين ──► جاري العمل ──► مكتمل مبدئياً ──► مغلق (معتمد)
                              │     ▲
                              ▼     │
                            معلّق ──┘
                       (سبب: قطع غيار/موافقة/مورد)
```

| الحالة | المسؤول | الإجراء |
|---|---|---|
| مفتوح | المستأجر / تنبيه وقائي / جولة | إنشاء البلاغ |
| معلّق للتعيين | مشرف الصيانة | تأكيد الأولوية + تعيين فني/مورد |
| جاري العمل | الفني | بدء العمل + تسجيل وقت البدء + صورة "قبل" |
| معلّق | الفني | تعليق مؤقت بسبب محدد |
| مكتمل مبدئياً | الفني | إنهاء + صورة "بعد" + مواد + ساعات |
| مغلق | المشرف / مدير المبنى | مراجعة واعتماد نهائي |

---

## 2. تغييرات قاعدة البيانات

### أ) توسعة enum الحالات
إضافة 3 قيم: `معلّق للتعيين`, `معلّق`, `مكتمل مبدئياً`. (نُبقي القيم الحالية للتوافق ونعيد تسمية UI: "جديد" = "مفتوح".)

### ب) أعمدة جديدة على `maintenance_requests`
- `request_source` (enum: `مستأجر`, `صيانة وقائية`, `جولة تفتيش`, `حادث أمني`, `إدارة`) — مصدر الطلب
- `started_at` timestamptz — وقت بدء التنفيذ الفعلي
- `completed_at` timestamptz — وقت الإنهاء المبدئي
- `hold_reason` text — سبب التعليق
- `materials_used` jsonb — قائمة `[{name, qty, unit_cost}]`
- `labor_hours` numeric — ساعات العمل
- `assigned_vendor_id` uuid (FK → vendors) — مورد خارجي بديل عن الفني
- `approved_by` uuid (FK → auth.users) — معتمِد الإغلاق
- `approved_at` timestamptz

### ج) Triggers
- توسعة `apply_wo_sla_defaults` ليحتسب `labor_cost` تلقائياً من `labor_hours × معدل` (اختياري — سنبقي إدخال يدوي مبدئياً).
- توسعة `validate_wo_closure`: لا يمكن الانتقال إلى `مغلق` إلا من `مكتمل مبدئياً` (إلا للـ super_admin).
- تحديث `stamp_mr_closure` لختم `approved_by`/`approved_at` عند الإغلاق النهائي.
- trigger جديد يختم `started_at` عند الانتقال لـ `جاري العمل`، و`completed_at` عند الانتقال لـ `مكتمل مبدئياً`.

## 3. تغييرات الواجهة (`src/routes/_authenticated/maintenance.tsx`)

### Kanban
- 6 أعمدة بدلاً من 4 (مع لون لكل حالة).
- زر "بدء" في عمود "معلّق للتعيين" يفتح modal تعيين فني/مورد.
- زر "تعليق" في "جاري العمل" يطلب السبب.
- زر "إنهاء" في "جاري العمل" يفتح modal الإنهاء (صورة بعد + مواد + ساعات).
- زر "اعتماد وإغلاق" في "مكتمل مبدئياً" — يظهر فقط لـ `maintenance_supervisor` / `super_admin`.

### نموذج إنشاء البلاغ
إضافة:
- حقل **مصدر الطلب** (Select).
- رفع **صورة "قبل"** إلى bucket `maintenance-photos` (موجود).

### Modal الإنهاء المبدئي (جديد)
- رفع صورة "بعد" (إلزامي).
- جدول مواد ديناميكي (اسم/كمية/سعر) — يحدّث `parts_cost`.
- إدخال ساعات العمل + تكلفة العمالة.
- ملاحظات إنجاز (إلزامي).

### Modal الاعتماد (جديد)
- عرض ملخص العمل + الصور + التكاليف.
- زر "اعتماد وإغلاق" أو "إرجاع للفني" (يرجّع الحالة لـ `جاري العمل` مع ملاحظة).

### عرض البطاقة (Kanban Card)
- شارة المصدر + الأولوية.
- thumbnail لصورة قبل/بعد إن وجدت.
- مدة منقضية (منذ البدء) للطلبات الجارية.

### جدول
عمود إضافي: المصدر، المعتمِد، تاريخ الإغلاق النهائي.

## 4. التفاصيل التقنية

**الملفات المعدّلة:**
- `src/routes/_authenticated/maintenance.tsx` — UI كامل لدورة العمل الجديدة.

**Migrations:**
1. `ALTER TYPE maintenance_request_status ADD VALUE` لكل حالة جديدة.
2. `CREATE TYPE wo_request_source AS ENUM (...)`.
3. `ALTER TABLE maintenance_requests ADD COLUMN ...` للأعمدة الجديدة.
4. تحديث triggers الموجودة + إضافة `stamp_wo_transitions`.

**Storage:** نستخدم bucket `maintenance-photos` الموجود لرفع before/after.

**صلاحيات:**
- الفني/أي مستخدم: ينقل من `جاري العمل` → `مكتمل مبدئياً` (إذا اكتملت البيانات).
- المشرف فقط: ينقل من `مكتمل مبدئياً` → `مغلق` أو يرجّع لـ `جاري العمل`.
- إعادة فتح المغلق: `super_admin` فقط (موجود بالفعل في `guard_wo_reopen`).
